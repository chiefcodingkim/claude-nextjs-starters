# PRD 작성 메타프롬프트: Notion 연동 견적서 웹 뷰어 & PDF 다운로드 (MVP)

> 이 문서는 Claude Code에 입력하여 `docs/PRD.md`를 생성하기 위한 **메타프롬프트**다.
> 아래 `---` 구분선 이후의 "프롬프트 본문"을 그대로 Claude Code에 붙여넣어 사용한다.

## 사용 방법

1. Claude Code를 프로젝트 루트(`invoice-web`)에서 실행한다.
2. 프롬프트 본문 전체를 붙여넣는다.
3. 생성된 `docs/PRD.md`를 검토하고, `[가정]`으로 표시된 항목과 "열린 질문"을 확정한다.
4. 확정된 PRD를 기반으로 다음 단계(로드맵/구현 계획)를 진행한다.

# 프롬프트 본문

## 역할 (Role)

당신은 10년 차 시니어 프로덕트 매니저이자 풀스택 아키텍트다. 작은 팀이 **2~3주 안에 출시 가능한 MVP**를 정의하는 데 능숙하며, 개발자가 추가 질문 없이 바로 구현에 착수할 수 있을 만큼 구체적이고 검증 가능한 PRD를 작성한다.

## 목표 (Goal)

아래 제품의 **MVP PRD 문서**를 `docs/PRD.md`에 한국어로 작성하라.

**제품 한 줄 정의**
프리랜서/소규모 사업자가 **Notion 데이터베이스에 입력한 견적서 데이터**를 **클라이언트가 고유 링크로 웹에서 확인**하고 **PDF로 다운로드**할 수 있는 견적서 웹 서비스.

**핵심 가치**
- 공급자(사용자): 익숙한 Notion에서 견적서를 작성하면 별도 입력 없이 전문적인 견적서 페이지가 만들어진다.
- 클라이언트: 로그인 없이 링크만으로 견적서를 보고, 인쇄/보관용 PDF를 받는다.

## 사전 조사 (반드시 먼저 수행)

PRD 작성 전에 다음을 읽고 기존 구조와 충돌하지 않게 하라.

1. `CLAUDE.md` — 프로젝트 아키텍처와 컨벤션
2. `app/layout.tsx`, `config/site.ts`, `components/ui/` — 현재 스타터킷 구조 파악
3. `package.json` — 설치된 의존성 확인 (없는 라이브러리는 "신규 도입"으로 명시)
4. Notion API, PDF 생성 방식 관련 최신 문서는 **context7 MCP**로 확인한다. 기억에 의존하지 말 것.

## 프로젝트 컨텍스트 (고정 제약)

| 항목 | 내용 |
|------|------|
| 프레임워크 | Next.js 15 App Router, React 19, TypeScript(strict) |
| 스타일 | Tailwind CSS v4 (`tailwind.config` 없음, `app/globals.css` CSS 변수 방식) |
| UI | shadcn/ui **base-nova 스타일 (Base UI 기반, Radix 아님)** → `asChild` 등 Radix 전용 API 가정 금지 |
| 구조 | 루트에 `src/` 없이 `app/`, `components/`, `lib/`, `config/`. 경로 별칭 `@/*` = 프로젝트 루트 |
| 레이아웃 | `ThemeProvider` → `SiteHeader` → `<main>` → `SiteFooter`, 다크모드 지원 |
| 단일 출처 | 사이트 이름/설명/내비게이션은 `config/site.ts` |
| 테스트 | 테스트 프레임워크 미설정 (PRD에 테스트 전략 필요 여부를 열린 질문으로 제시) |
| 언어 | 문서/주석/커밋은 한국어, 변수·함수명은 영어, 들여쓰기 2칸 |

## MVP 범위 정의 (Scope)

### 반드시 포함 (In Scope)
1. **Notion 연동**: Notion 데이터베이스(견적서 목록)와 하위 항목(품목 라인)을 서버에서 조회한다. 인증은 Notion Integration Token(서버 환경변수)을 사용한다.
2. **견적서 웹 뷰어**: 고유 URL(예: `/invoice/[id]` 또는 공유 토큰 기반)로 견적서를 읽기 전용으로 렌더링한다. 반응형 + 다크모드 대응.
3. **PDF 다운로드**: 웹에서 보이는 견적서와 동일한 내용을 PDF 파일로 내려받는다. 한글 폰트가 깨지지 않아야 한다.
4. **접근 제어(최소)**: 추측 불가능한 링크(토큰/UUID)로 접근을 제한한다. 로그인 없음.
5. **오류/빈 상태 처리**: 존재하지 않는 견적서, Notion API 실패, 권한 없음, 로딩 상태.

### 명시적으로 제외 (Out of Scope — PRD에 "비목표"로 기재)
- 견적서 작성/편집 UI (작성은 Notion에서만)
- 사용자 계정/로그인/결제/전자서명
- 이메일 발송, 알림, 승인/거절 워크플로
- 다국어, 다중 통화 환산, 세금 규칙 자동화
- 자체 데이터베이스 (Notion이 단일 데이터 원천)

> 위 범위를 넓히고 싶으면 임의로 추가하지 말고 "향후 확장(Post-MVP)" 섹션에만 기재하라.

## PRD에 반드시 포함할 구조

다음 목차 순서를 지켜 작성하라.

1. **개요**: 배경, 문제 정의, 제품 비전, 한 줄 요약
2. **목표와 성공 지표**: 정량 지표(예: 링크 오픈 → PDF 다운로드 전환, 페이지 로드 시간 목표, PDF 생성 시간 목표)와 MVP 완료 기준
3. **사용자 및 페르소나**: 공급자(견적서 작성자), 클라이언트(열람자) — 각 목표/불편/시나리오
4. **사용자 여정**: 공급자 플로우, 클라이언트 플로우를 단계별로 (Mermaid `flowchart` 사용 가능)
5. **기능 요구사항**: ID(`FR-001` …), 우선순위(P0/P1), 설명, **수락 기준(Given/When/Then)** 형태의 표
6. **비기능 요구사항**: 성능, 보안(토큰 노출 금지, 링크 추측 방지), 접근성, 브라우저 지원, 한글 PDF 품질, 캐싱/재검증 전략(Notion API 속도·레이트리밋 고려)
7. **데이터 모델**: Notion 데이터베이스 스키마 제안(속성명, 타입, 필수 여부, 예시 값)과 이를 매핑한 TypeScript 타입(`Invoice`, `InvoiceItem`, `Client` 등). 합계/세액 계산을 어디서 하는지(Notion 수식 vs 앱) 결정 및 근거 명시
8. **화면 및 라우팅 설계**: 페이지 목록, URL 구조, 각 화면의 구성요소(와이어프레임은 ASCII), 사용할 shadcn/ui 컴포넌트와 신규 추가 필요한 컴포넌트(`npx shadcn@latest add` 대상)
9. **기술 아키텍처**: 기존 구조 위에 추가될 디렉터리/파일 배치안(`app/`, `components/`, `lib/notion/`, `lib/pdf/` 등), Server Component/Route Handler 역할 분담, 환경변수 목록(`.env.example`)
10. **PDF 생성 방식 비교 및 결정**: 최소 3가지(예: `@react-pdf/renderer`, Puppeteer/Playwright 서버 렌더링, 브라우저 `window.print`/html2canvas) 장단점을 표로 비교하고, **MVP에 하나를 추천**(한글 폰트, Vercel 서버리스 제약, 번들 크기, 웹과의 디자인 일치도 기준)
11. **보안 및 개인정보**: Notion 토큰 관리, 링크 공유 모델의 위험, 접근 로그 여부, 민감 정보(금액/사업자 정보) 취급
12. **마일스톤 및 구현 순서**: 1~3주 단위로 쪼갠 작업 단위(각 단위는 독립적으로 검증 가능), 의존성, 예상 공수(S/M/L)
13. **리스크 및 대응**: 기술/운영/일정 리스크와 완화책 (Notion 레이트리밋, PDF 한글 폰트, 서버리스 타임아웃 등)
14. **열린 질문**: 사용자 확정이 필요한 결정 사항을 번호 목록으로 정리 (예: 링크 방식, 배포 플랫폼, 사업자 정보 입력 위치)
15. **향후 확장 (Post-MVP)**

## 작성 규칙 (Constraints)

- **모든 본문은 한국어**로 작성한다. 코드 식별자와 기술 용어는 영어 그대로 둔다.
- 확인되지 않은 사실은 단정하지 말고 `[가정]` 태그를 붙여라. 라이브러리 동작은 context7로 확인한 내용만 사실로 서술한다.
- 모호한 표현("빠르게", "적절히")을 금지한다. 측정 가능한 수치나 조건으로 쓴다.
- 모든 기능 요구사항은 **테스트 가능한 수락 기준**을 가져야 한다.
- MVP 범위를 지켜라. 범위 밖 아이디어는 15번 섹션에만 둔다.
- 기존 프로젝트의 컨벤션(`@/*` 별칭, `config/site.ts` 단일 출처, Base UI 기반 shadcn)을 위반하는 설계를 제안하지 않는다.
- 분량: 전체 약 400~700줄 이내. 표와 목록을 적극 활용하고 장황한 서술은 피한다.
- 이 단계에서는 **PRD 문서만 작성**한다. 앱 코드를 수정하거나 패키지를 설치하지 않는다.

## 진행 방식

1. 사전 조사 결과를 3~5줄로 먼저 요약해 보고한다.
2. 열린 질문 중 **작성에 반드시 필요한 것**(최대 3개)만 먼저 사용자에게 묻고, 나머지는 `[가정]`으로 진행한다.
3. `docs/PRD.md`를 작성한다. (`docs/` 폴더가 없으면 생성)
4. 작성 후 아래 **자체 검증 체크리스트**를 점검하고 결과를 보고한다.

## 자체 검증 체크리스트

- [ ] 15개 섹션이 모두 존재하는가
- [ ] 모든 `FR-*`에 우선순위와 수락 기준이 있는가
- [ ] Notion DB 스키마와 TypeScript 타입이 서로 일치하는가
- [ ] PDF 방식 3가지 이상을 비교하고 근거 있는 추천을 제시했는가
- [ ] 한글 폰트/서버리스 제약이 리스크에 반영되었는가
- [ ] 비목표가 명확하고 MVP가 2~3주 안에 가능한 규모인가
- [ ] 기존 구조(`app/`, `@/*`, Base UI shadcn, Tailwind v4)와 충돌하는 제안이 없는가
- [ ] `[가정]`과 열린 질문이 구분되어 정리되어 있는가

## 최종 출력

- 파일: `docs/PRD.md`
- 채팅 응답에는 문서 전체를 반복하지 말고, **핵심 결정 사항 5줄 요약 + 열린 질문 목록 + 체크리스트 결과**만 보고한다.
